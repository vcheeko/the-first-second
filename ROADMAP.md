## Next safe development sequence

### v0.3 — First playable experiment

Goal: build the smallest simulation that can demonstrate the core inversion:

> More seconds increase local stability; fewer seconds increase exposure to reality boundaries.

The first experiment should contain only:

- one local world;
- one player state;
- a visible or inspectable seconds value;
- a stability model;
- at least three anomaly types;
- one transition boundary;
- one observable consequence of reaching a low-second state.

It does not need final graphics, multiplayer, open-world content, or a commercial game engine commitment.

### v0.4 — Identity and memory

Test whether a player can cross a simulation boundary while preserving enough state to feel like the same entity.

Focus:

- memory persistence;
- memory corruption;
- state transformation;
- branch / copy ambiguity;
- continuity rules.

### v0.5 — Nested simulation prototype

Add a second simulation capable of having different rules and a different local clock.

Test:

- simulation-to-simulation transition;
- unequal time rates;
- incompatible player forms;
- transfer of memory and seconds.

### v0.6 — The First Second entity

Introduce a constrained version of The First Second.

The entity should demonstrate cross-simulation memory and movement without becoming omnipotent or simply explaining the entire mystery.

### v0.7 — Multiplayer model

Only after the single-player simulation rules are coherent, test multiple players with:

- unequal seconds;
- different simulation layers;
- asymmetric perception;
- shared and contradictory events;
- cross-layer interaction.

## Legal / identity hold points

These items are deliberately **not** executed automatically:

- paid trade mark filing;
- use of the ® symbol;
- third-party commercial licensing;
- acceptance of substantive outside contributions without written rights terms;
- incorporation of third-party copyrighted assets without verified permission.

The working title remains **THE FIRST SECOND** while name clearance continues.

## Design principle

Do not solve by documentation what should be discovered by a playable experiment.

Each version should reduce uncertainty and leave an auditable Git history of what changed and why.
